## High

### H1. Event snapshot retries re-spend the $5 cap on every attempt
`lib/watchers/events/worker.ts:486`, `lib/watchers/events/jobs.ts:65-68`

`runDueSnapshots` gives each attempt `maxCostUsd: Math.min(snapshotCap, runCap - spent)`, where `spent` counts only this process. Nothing counts what earlier attempts of the same slot already spent, which is the gap 4.9 closed for the weekly worker with `weeklySpend()`. On top of that, `abandonActiveJobs` *decrements* `attempts` on SIGTERM, so attempts stopped by a deploy never reach `MAX_ATTEMPTS`.

- **Failure scenario:** an event snapshot takes about 10 minutes at concurrency 12. Three pushes to main in that window each SIGTERM the container. Each hourly retry claims the job again with a fresh $5, so one slot costs about $20. A busy deploy day has no upper bound. Ordinary failed attempts (no SIGTERM) still allow 3 × $5.
- **Suggested fix:** before each attempt, sum what this slot's earlier event runs spent (`spentSoFar` on runs with `kind: "event"` for the item since the first claim, or store a running total on the WatcherJob), and pass `snapshotCap - earlier` as the cap. Skip the attempt when less than $1 is left. Also give the event watcher a per-day or per-week cap that reads earlier runs, rather than a $15 cap per hourly process.

## Medium

### M1. A failed model-switch run stores no cost, so the daily switch cap undercounts
`lib/watchers/models.ts:452`, `:457`, `:183`

The catch marks the run failed without `costUsd`. `spentToday` uses `_sum: { costUsd }`, which ignores nulls. In the same process, `budget.switch += outcome.costUsd` only includes pipelines that finished. A failed run isn't "done", so the resume re-asks both models.

- **Failure scenario:** the old-model pass spends $3 and the new-model pass then throws on a database error. The run is stored as `failed` with a null cost. The next run resumes the switch for that item with the full $12 cap, and the $3 is never counted.
- **Suggested fix:** in the catch, store `costUsd: await spentSoFar(db, run.id)` and add the same amount to `budget.switch`. Make `spentToday` fall back to `spentSoFar` when `costUsd` is null, the way `weeklySpend` does.

### M2. The snapshot cap counts answers only and overshoots with 12 calls in flight
`lib/snapshots/run.ts:121-126`, `:142`

`onAnswer` adds only `e.result.cost.usd`. Extraction, the fresh-set generation and theme mapping aren't counted. With `askConcurrency: 12`, up to 11 calls already in flight finish after the abort, and their extractions still run (`extractionSignal` is the outer signal). The weekly and event caps then subtract `result.costUsd`, which includes all of those costs, so the per-item cap is not the ceiling it reads as.

- **Failure scenario:** with the item cap at $6, answers reach $6.01, 11 more calls land, and every answer is extracted. The run's `costUsd` comes to about $8–9, which takes more of the shared $15 run cap than planned.
- **Suggested fix:** count extraction cost as each one finishes, and subtract `set.costUsd` from the budget before asking. Stop starting new calls once `spent + inFlight × estimated cost per call` would cross the cap. Or document the cap as covering answers only and set the item and run caps with that headroom in mind.

### M3. The weekly worker loses a thrown snapshot's spend for the rest of the run
`lib/worker/weekly.ts:179`, `:133`, `:205-216`

`spent += result.costUsd` only runs when `snapshot()` returns. `earlier.total` is read once, before the loop. If `runSnapshot` throws after spending money (for example `runPipeline` rejecting, see M5), the catch doesn't add what that run spent.

- **Failure scenario:** item 1 spends $5 and then throws. `spent` stays at 0, so items 2 and 3 each get up to $6 under a run cap that still shows $15 left. The week ends over its cap. A later re-run is correct, because `weeklySpend` reads the stored answers.
- **Suggested fix:** in the catch, add `spentSoFar(db, runId)` for the run that failed to `spent`. Find it the same way the catch already finds the run it marks failed, or have `runSnapshot` attach `runId` to the error it throws.

### M4. Alerts can be stuck in `sending`, and a sent email can be recorded as failed
`lib/alerts/after-snapshot.ts:244-255`, `lib/alerts/withdraw.ts:32`

`deliver` claims an alert by setting `pending → sending`, sends it, then sets `sent`. (a) If the process dies between the claim and the update (a deploy SIGTERM is enough), the alert stays in `sending` for good. Nothing resets it, it isn't in `REPORTED_ALERT_STATUSES` (so reports and the connector hide it), and `withdrawAlerts` refuses it forever with "try again in a minute". (b) The `try` also wraps the update to `sent`. If the email went out but that write fails, the alert is marked `failed`.

- **Failure scenario:** a deploy lands while the weekly worker is sending alert A-12. The email reaches the team, but A-12 never appears in the monthly report or `list_alerts` and can't be withdrawn.
- **Suggested fix:** move the update to `sent` out of the send's `try`, and on failure log "sent, status not saved" rather than marking the alert failed. Add a sweep for alerts in `sending` older than about 15 minutes: set them to `sent` with a note saying the outcome is unknown (don't resend). Let `withdrawAlerts` accept a stale `sending` alert.

### M5. One failed database write rejects the whole run and leaves it `running`
`lib/pipeline/run.ts:145-202`, `:209`

The per-call tasks are joined with `Promise.all`. A thrown `answer.create`, `extraction.create` (the fallback in `extractAndStore`) or `getExtractionModel()` rejects the run straight away. The other provider calls keep running and billing, their costs never reach `RunPipelineResult`, and the final `run.update` never runs.

- **Failure scenario:** one short Postgres error during a weekly snapshot. The item's Run stays `running`, which blocks the item for 3 hours (`STALE_RUNNING_MS`) and the event watcher's `busy` check. M3 then drops its spend. A public run stays `running` for good, and the route counts a flat $1 estimate.
- **Suggested fix:** use `Promise.allSettled`, catch each task's errors so a failed write becomes a failed answer, and always finish the Run (`failed` or `partial`) in a `finally`.

## Low

### L1. An "unclear" model check is paid again on every run that day
`lib/watchers/models.ts:205`, `:210`, `:228-231`

Only `unchanged` refreshes `confirmedAt`, and the $1 check cap starts at 0 in each process. Railway runs the cron on every deploy, so a provider left `unclear` is checked again, and paid for again, each time.

- **Suggested fix:** record the check (time and cost) for `unclear` too, for example in a `lastCheckedAt` field or a WatcherJob keyed `models:check:<provider>:<day>`. Read today's check spend from the database the way `spentToday` reads switch spend.

### L2. A paid extraction is recorded at $0 when its database write fails
`lib/extraction/store.ts:61-73`

If `extractAnswer` succeeds but the `$transaction` throws, the catch writes a failed Extraction with no cost and returns `costUsd: 0`. `spentSoFar` and every cap then miss that call.

- **Suggested fix:** keep `out.costUsd` from before the transaction, and store it on the failed row and in the return value.

### L3. A monthly report killed mid-send can be sent twice
`lib/reports/monthly.ts:125-147`, `scripts/monthly-report.ts`

The monthly-report script is the only cron without `releaseOnSigterm`. That's deliberate, since releasing would allow a resend. But if the process dies after SendGrid accepts the email, the job stays `running`, and after `STALE_JOB_MS` (50 minutes) any run started by a deploy takes the job again and sends it again. The "outcome unknown → complete" guard only covers errors that are caught.

- **Suggested fix:** on SIGTERM, mark a `sending` monthly job `complete` with a note that the outcome is unknown. Or treat a stale `running` job of kind `monthly_report` as "skip and report" instead of retrying it.

### L4. MCP: `snapshotById` accepts any run kind or status
`AI Topic Explorer MCP/src/logic/common.ts:76-81` (used by `compareText` and `describeSnapshot`)

`snapshots()` filters to `SNAPSHOT_KINDS` and finished runs, but `snapshotById` doesn't. An explicit id can therefore point at a `model_switch` run, which mixes the old and new model's answers, or at a run still in progress.

- **Failure scenario:** a user passes a model-switch run id as `after_snapshot_id`. The compare mixes both models' answers and reports swings that aren't real.
- **Suggested fix:** apply the same `kind` and `status`/`finishedAt` filter, and return a `UserError` explaining why when the run doesn't qualify.

## Checked and found sound

- **Rate limit:** the atomic upsert in `lib/rate-limit.ts` is race-free.
- **Daily spend cap:** the cap and its one-time alert flag (`lib/guards/spend.ts`) are correct. Runs in progress can overshoot, as its comment says.
- **Public route:** `/api/analyze` records an estimate when a run fails.
- **WatcherJob claims:** the claim is optimistic (`attempts` plus `status` in the WHERE), so it is race-safe.
- **Alert creation:** alerts are made once per run, with a `P2002` fallback.
- **Withdrawn alerts:** they are excluded everywhere alerts are shown: the monthly load and the MCP's `list_alerts`, `explain_alert` and `list_watch_items`.
- **MCP preview → confirm:** single use, creator only, same tool and time-limited, with one conditional UPDATE. `applyReview` checks `status = pending` inside a transaction.
- **MCP usage log:** fire-and-forget, so it never breaks or blocks a call. No user input reaches the SQL.
- **MCP vendored files:** they match the app's `origin/main` byte for byte (only the declared shims differ).
