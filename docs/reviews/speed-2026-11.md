# Speed audit: public site, mobile and desktop (task 6.4)

Run 2026-11-07 against production (aitopicexplorer.app), with the Google PageSpeed Insights API (Lighthouse lab data) plus a source read and one live analysis. This is a review only: nothing in the app was changed. Task 6.6 works through the ranked fixes below.

**Bottom line:** the site is already fast. Every page scores 86–100 on performance. The few things holding scores down share one or two causes, and the biggest is a one-component fix: **the beta banner is rendered only in the browser**, so it pops in after hydration, causing all the layout shift on every page and becoming the slowest-painting element on the results pages.

## Ranked fixes

Ordered by expected gain for the effort. Gains are Lighthouse's estimates or my reading of the trace, on mobile unless noted.

### 1. Render the beta banner on the server — biggest win, small change

- **What:** `BetaBanner` uses `useSyncExternalStore(subscribe, isDismissed, () => true)`. The server snapshot says "dismissed", so the server HTML has no banner, and it's inserted after the JS hydrates. That insertion pushes the whole page down ~47–62 px.
- **Evidence:** it is the only layout shift Lighthouse finds on every page (`div.min-h-screen` shifted, 0.075 mobile / 0.035 desktop). On both results pages the banner paragraph is the LCP element, so LCP waits for hydration: element render delay 0.54 s (old result) and 2.49 s (new results); old-result mobile LCP is 3.7 s, and the new results page's 4.1 s Speed Index comes from the late visual change.
- **Fix:** render the banner in the server HTML by default and hide it before first paint when dismissed. Either read a cookie in the layout (set the cookie on dismiss alongside or instead of localStorage), or keep localStorage and add a tiny inline `<script>` in `<head>` that sets `data-beta-dismissed` on `<html>`, with CSS `html[data-beta-dismissed] .beta-banner { display: none }`. Keep the client component only for the dismiss button.
- **Expected gain:** CLS to ~0 on all pages; old-result mobile LCP from 3.7 s to ~1.1 s (performance 86 to mid-90s); new-results Speed Index from 4.1 s to ~1.5 s.
- **Files:** `components/BetaBanner.tsx`, `app/layout.tsx`, `app/globals.css`.

### 2. Stop shipping the markdown renderer to pages that don't use it, and consider rendering it on the server

- **What:** `app/results/[id]/page.tsx` imports both `ResultsContent` (old layout) and `RunResultsContent` (new layout). Both are client components, so they land in one route chunk (`20h105n6it78-.js`, 57 KB compressed / 190 KB raw) that also contains `react-markdown`, `remark-gfm`, micromark, mdast and hast via `AnswerTabs` → `AnswerProse`. An old saved result downloads all of it and uses about 5 KB (Lighthouse: 52 KB of 57 KB unused). On the new layout the markdown is parsed in the browser during hydration.
- **Fix, in two steps:**
  - Easy: load the two layouts with `next/dynamic` (or split the route's client entry) so each result type downloads only its own layout.
  - Bigger: `AnswerProse` has no hooks, so it can run as a server component. Render each answer's prose on the server and pass the rendered nodes to `AnswerTabs` as props or children, keeping only the tab switching and collapse logic on the client. `react-markdown` and `remark-gfm` then never reach the browser. Trade-off: rendering all four answers server-side adds their HTML to the page; render only the first tab eagerly or hide inactive panels with `hidden` and compare the totals.
- **Expected gain:** about 40–50 KB compressed JS off results pages. Lighthouse estimates 750 ms LCP (old result) and 300 ms FCP/LCP (new results) from unused JS on mobile; less main-thread parsing at hydration.
- **Files:** `app/results/[id]/page.tsx`, `app/results/[id]/RunResultsContent.tsx`, `components/AnswerTabs.tsx`, `components/AnswerProse.tsx`.

### 3. Load Google Analytics after the page is idle

- **What:** `gtag.js` is the largest script on every page (181 KB compressed, 76 KB unused) and owns the top long tasks on the home page (138 ms and 118 ms) plus 130–220 ms of main-thread time per page. It loads with `strategy="afterInteractive"`.
- **Fix:** switch both GA `<Script>` tags to `strategy="lazyOnload"`. Trade-off: a visitor who leaves within the first second or two may not be counted; acceptable for a public explorer.
- **Expected gain:** home mobile TBT from 220 ms to under 100 ms (the only lab CWV over target on home), TTI about 0.5 s sooner on every page.
- **File:** `app/layout.tsx`.

### 4. Shrink the data sent to the browser on results pages

- **What:** results pages serialize their props into the HTML for hydration. On the old saved result that payload is **139 KB of the 193 KB** HTML (50 KB compressed), mostly `providerTexts`: every AI's full raw answer, sent so the word-context modal can search it. On the new layout it is 46 KB of 110 KB (`answerTexts` and the full `view`).
- **Fix:** look up word context on demand (a server action or small route that takes the analysis id and word) rather than shipping every raw answer; pass client components only the fields they render. Pairs well with fix 2.
- **Expected gain:** roughly 30 KB compressed off old results and 10–15 KB off new ones; less JSON to parse at hydration.
- **Files:** `app/results/[id]/page.tsx`, `app/results/[id]/ResultsContent.tsx`, `app/results/[id]/RunResultsContent.tsx`, `lib/analysis/word-context.ts`.

### 5. Cache saved results pages

- **What:** a saved result never changes, but `/results/[id]` renders on every request with `cache-control: private, no-cache, no-store` and two database reads (`analysis`, then `loadRunView`). The home page, by contrast, is prerendered (`x-nextjs-cache: HIT`).
- **Fix:** make the route cacheable: ISR with `generateStaticParams` returning `[]` and `revalidate = false`, or `"use cache"` around the loaders. Don't cache the unreadable/not-found branches.
- **Expected gain:** 50–100 ms TTFB per view and no database load from shared links going viral. Modest for speed, useful for cost and resilience.
- **File:** `app/results/[id]/page.tsx` (plus `lib/results/run-view.ts` if using `"use cache"`).

### 6. Inline the CSS

- **What:** the one stylesheet (10 KB) blocks first paint. Lighthouse estimates 140–300 ms FCP/LCP on mobile.
- **Fix:** `experimental: { inlineCss: true }` in `next.config.ts`. The CSS is small, so inlining it costs little on repeat views.
- **Expected gain:** about 150 ms mobile FCP on every page.
- **File:** `next.config.ts`.

### 7. Don't preload the mono font

- **What:** every page preloads two `.woff2` files (23 KB and 49 KB). One is Geist Mono, used only for the model name in the answer tab and the timer in the progress panel.
- **Fix:** `preload: false` on `Geist_Mono` (or use a system mono stack). Confirm which preload is which in the network panel first.
- **Expected gain:** about 23 KB off the critical path on mobile; small.
- **File:** `app/layout.tsx`.

### 8. Find the source of the 14 KB of legacy polyfills

- **What:** the shared chunk `3clkpj849lgrm.js` carries polyfills for `Array.prototype.at`, `flat`, `flatMap`, `Object.fromEntries`, `Object.hasOwn`, `trimStart`/`trimEnd`, which every supported browser already has.
- **Fix:** run the bundle analyzer to find which module adds them. If it's Next's own targets, add a modern `browserslist` to `package.json`; if it's a dependency, replace it or leave it.
- **Expected gain:** 14 KB, ~0–150 ms on mobile.
- **Files:** `package.json` (browserslist), possibly a dependency.

### 9. Housekeeping: Footer changelog in the JS bundle

- **What:** `components/Footer.tsx` is a client component with the whole `CHANGELOG` array inline, so every release adds to the JS on every page.
- **Fix:** make `Footer` a server component and keep only the changelog modal on the client, passing the entries as props, or load them when the modal opens.
- **Expected gain:** a few KB today, growing with each release.
- **File:** `components/Footer.tsx`.

## Live analysis (one run, ~$0.14)

Topic "Community solar programs in Texas", run in the in-app browser on desktop (result: `/results/cmw71b2cf00j20xqvdmkl37ml`).

- The `/api/analyze` stream took 62 s and carried only 726 bytes of progress events. Moving to the results page took 113 ms (one RSC fetch, 14 KB); the results chunk was already cached.
- No long tasks and no layout shifts were recorded during the stream (PerformanceObserver). Caveat: the browser pane was in the background, so timers were throttled; repeat on a visible phone for a firmer read.
- The 1-second elapsed timer (`setProgress` in `app/page.tsx` around line 344) re-renders the whole home page component each tick. Harmless today; if 6.6 is in the file anyway, move the timer into `AnalysisProgressPanel` so only the panel re-renders. Low priority.
- Perceived speed, not measured speed, is the issue during a run: about a minute with the same "Reading the answers…" status. That's a design question for 6.5 rather than a performance fix.

## Method and gaps

- PageSpeed Insights API v5, mobile and desktop, all four categories, run in parallel at 2026-11-07 23:25 UTC. One run per page and strategy, so treat single-digit score differences as noise.
- JS chunks fetched from production and fingerprinted to map them to components (`20h105n6it78-.js` = results layouts + markdown; `2w3ruom2gvama.js` = home page; `3clkpj849lgrm.js` = framework/shared).
